## 1. WebP with raster fallbacks

Every image ships as WebP with a JPEG (or PNG, where there is an alpha
channel) partner behind a `<picture>` element.

- **87 fallbacks** generated by `scripts/images.mjs` — 63 bundled,
  13 certificates, 11 insight photographs.
- **13 render sites** converted across 8 components.
- A WebP-capable browser fetches **only** the WebP. Measured across 12
  routes: `raster fetched: 0` everywhere. There is no double download.

### The detail that made this safe

`<picture>` is a real element with a box of its own (`display: inline`).
Wrapping thirteen tuned images in one would have changed the layout
tree — several are `absolute inset-0` inside a positioned parent, others
are `h-full w-full` inside a flex or grid cell, where an inline wrapper
becomes the flex item and `h-full` starts resolving against `auto`.

Every wrapper is `display: contents`, which removes its box from the
layout tree while keeping its children. The `<img>` keeps the exact
position in the box tree it had before. Measured CLS after the
conversion: **0, 0.0003, 0, 0.0001**.

### Two mistakes made and corrected during the work

- The first version encoded fallbacks over the top of their own source,
  which destroyed `hero-no-bg.png` — an 804KB master — by replacing it
  with a transcode of the lossy WebP. Restored from backup. Transparent
  fallbacks now take an explicit `-fallback.png` suffix so a master is
  never the output path, and the encoder reads its source into a buffer
  before writing anything.
- `Picture` began as a plain function component, which silently dropped
  the `ref` the insights carousel uses to read `naturalWidth` off a
  frame. Both variants now forward refs to the `<img>`.

## 2. Security

### Dependency CVEs — 3 → 2, and the 2 are not exploitable here

`nanoid` (high) was fixed with an `overrides` pin to `^3.3.18`. It
reaches the project only through `postcss`, so it was build-time and
never shipped, but the pin is free.

The two react-router advisories are **left deliberately**, and this is
the reasoning rather than an omission:

- *Open redirect via backslash in `<Link>`/`useNavigate`* — needs a URL
  from untrusted input to reach a navigation call. Every `to=` and
  `navigate()` in this codebase is a hardcoded literal or a slug from
  the site's own data files. Nothing user-supplied routes.
- *Arbitrary constructor injection via `deserializeErrors()`* — requires
  React Router's SSR hydration path. This is a pure client SPA on
  `BrowserRouter`; `StaticRouter` and `renderToString` appear nowhere.

The fix is react-router **7.x** — a major upgrade, days of churn, on the
library the Next.js migration removes entirely. Fixing it now would be
risk spent on a dependency that is about to be deleted.

### `public/_headers` — added, there was none

A full set, with a CSP tight enough to be worth having:

- `script-src 'self'` with **no** `unsafe-inline`. Confirmed against
  every route — the JSON-LD blocks are `application/ld+json`, which is
  data, so nothing is blocked and nothing is loosened for them.
- `style-src` does need `'unsafe-inline'`, and that is not laziness:
  React renders `style={{…}}` as a style attribute and motion writes
  transforms into that attribute every frame. No nonce or hash
  mechanism covers attribute styles.
- `frame-ancestors 'none'`, `base-uri 'self'`, `object-src 'none'`,
  nosniff, HSTS, a closed `Permissions-Policy`.
- Caching: `immutable` for content-hashed `/assets/*`, revalidate for
  documents so a stale deploy can't serve last build's canonical.

**Zero CSP violations** across 13 routes × 2 viewports, tested by
injecting the real header from `_headers` onto every response.

## 4. Performance

CLS is effectively zero everywhere. Desktop is fast. The mobile numbers
have one dominant cause, and it is not a defect.

| Route | Desktop | Mobile, 4× CPU | Mobile, 4× CPU + Fast 3G |
|---|---|---|---|
| `/` | LCP 2096ms | 2712ms | 6124ms |
| `/projects/saturdays` | LCP 236ms | 592ms | 4020ms |

### The hero intro owns ~1.7s of LCP

`useIntroSequence` stages the hero on `T_REVEAL = 1800ms`; the portrait
is the LCP element and does not paint until the reveal. Measured with
the intro suppressed:

| | with intro | without |
|---|---|---|
| desktop | 2096ms | **348ms** |
| mobile 4× CPU | 2712ms | **996ms** |

**This is a design decision and it is yours to make.** Desktop at 2.1s
still sits inside Google's "good" band (<2.5s); a real mid-range phone
will often not. Given how much weight you are putting on ranking, the
options are worth stating plainly:

1. **Keep it.** The choreography is the first thing the site says.
   Note that any scroll, tap or keypress snaps straight to the finished
   state, and reduced-motion users start there — so the slow path is
   only for someone who lands and waits.
2. **Shorten it.** `useIntroSequence.ts` warns that `T_REVEAL` cannot
   lead the letter spring, which does not settle until ~1.6s. The
   spring has to be made faster first.
3. **Decouple the LCP element** — let the portrait paint early and keep
   the staging on everything around it.

### The rest of the mobile gap is the SPA itself

156KB gzip of JavaScript in one chunk must download, parse and execute
before anything renders. That is exactly what server rendering fixes,
which is the migration you already have planned — so no code splitting
was done here that the migration would only throw away.

Done regardless: the hero WebP is now preloaded from the document with
its real hashed URL, injected by `seo-build.mjs`, typed `image/webp` so
non-WebP browsers skip it. It moved little over localhost, which is
itself the finding — the image was never the bottleneck — but on a real
connection it removes the round trip that waits on the bundle.

# Mobile performance — 21 August 2026

The question was whether the project deck and the insights carousel lag
on old phones, and whether their interactions had to be stripped to fix
it. Measured first, and the answer changed the plan: **nothing was made
less interactive. Every drag, step, autoplay, lightbox and overlay is
exactly as it was.**

## What was actually slow

Not the JavaScript. Across a full-page scroll at 6x CPU throttling the
site runs **zero long tasks** — the scroll handlers, the scroll-linked
transforms and the spring animations are all comfortably inside frame
budget. `npm run audit:scroll` puts the two sections in question at
7.1ms p95 with no janked frames, on the slowest profile tested.

The cost was memory, and it was large:

| | before | after |
|---|---|---|
| decoded bitmaps, phone | **133.5 MB** | **10.5 MB** |
| decoded bitmaps, desktop | 156.4 MB | 36.8 MB |
| images decoded oversized | 19 | **0** |
| long tasks while scrolling | 0 | 0 |

A decoded image costs `width x height x 4` bytes whatever the file
weighed. A 2048x1152 WebP is ~240KB on the wire and **9.4MB in RAM**,
and nineteen images were being decoded at master size into boxes a
third as wide. On a phone with 2-3GB shared between the OS and the
browser, that is what produces memory pressure, GC pauses, and
eventually the tab being evicted and reloaded — the worst "lag" there
is, because the page starts over.

## Two fixes, neither of which touches behaviour

**A width ladder on every image.** `scripts/images.mjs` now emits 400 /
800 / 1200 / 1600px renditions alongside each master, and `<picture>`
carries a srcset plus a real `sizes` derived from the grid each image
sits in. The browser downloads and decodes the rung that fits the box.
Cost: **+5.5KB gzipped** of bundle. Return: **92.7% less decoded
memory on a phone.**

**The carousel's side mirrors are now a wide-screen effect.** They fill
the slack either side of a photograph narrower than its card — and
`npm run audit:mirrors` measured that slack at **1px on a phone** and
69-113px from 768px up. Below that they were clipped entirely out of
view while still costing a `blur(24px)` plus a gradient mask each,
across up to five slides. Ten of the most expensive layers on the page,
painting pixels nobody could see, on the hardware least able to afford
it. Gated at 768px: 6 blurred layers on a phone became **0**, tablet
and desktop unchanged.

## Three things found along the way

- **The generated module fed itself.** `importedAssets()` scanned all
  of `src/`, which includes its own output — so renditions were read
  back as masters and the next run built renditions of renditions. One
  pass took 63 images to 606 and wrote 768 files named things like
  `algoverse_arena-1200-800-400.webp`. Both the src scan and the
  public scan now exclude the generated shape, with a second guard on
  the `<name>-<width>` pattern.
- **A second raster ladder cost more than it was worth.** Every
  rendition must be imported to learn its hashed URL, and those URLs
  are strings in the bundle: the raster ladder alone added ~140KB raw /
  26KB gzipped, spent entirely on browsers without WebP. Removed. Those
  browsers still get one correct, sharp full-size fallback.
- **The hero preload went stale the moment srcset landed.** It named
  the master while the page rendered a rendition, so mobile downloaded
  a file it never used. It now carries `imagesrcset` and `imagesizes`
  matching the `<img>`; verified at exactly **one** hero request per
  load on both phone and desktop. `HERO_SIZES` in `scripts/seo-build.mjs`
  must stay in step with the hero's `sizes` in `src/HeroSection.tsx`.

## Also done

- `assetsInlineLimit: 0` — Vite was inlining the smallest renditions as
  base64 into the bundle, which is bytes that must be parsed before
  first paint, cannot be cached separately, and cannot be skipped when
  the browser picks a different rung.
- **Four identical copies of `useMediaQuery`** — in HeroSection,
  SelectedWorks, ExperienceRoles and ProjectPage — consolidated into
  `src/lib/useMediaQuery.ts`. It resolves synchronously in the
  initialiser, which is load-bearing: several callers switch layout on
  it, and a hook reporting `false` until after first paint would render
  the wide branch for a frame on every phone. One `typeof window` guard
  to keep SSR-safe through the Next.js move, instead of four.

## Verification

`npm run audit` reports **0 findings** across 13 routes x 2 viewports,
which includes horizontal-overflow and tap-target checks at 390px. SEO
holds at 0, `<picture>` at 157 images with no double downloads, and all
87 fallbacks still fetch and decode.

New commands: `audit:mobile`, `audit:scroll`, `audit:mirrors`.

## The mobile variant

One section renders differently below 768px: the project deck. The
insights carousel is untouched at every width, on the author's
instruction. Nothing at 768px and above changes at all.

| | phone (390px) | tablet / desktop |
|---|---|---|
| `#work` sticky layers | **0** | 11 |
| `#insights` | carousel, unchanged | carousel, unchanged |

**`WorksListMobile`** replaces the scroll-linked deck with a plain list
of the same ten projects — same covers, same result band, same link. The
deck is the best thing on the site at 1440px and the wrong thing at
390px: ten viewports plus a dwell each makes the section roughly twenty
screens tall, the pinning fights the browser's own scroll handling
(worst on iOS, where the compositor is already running address-bar

covers with 70px-blur shadows is ten large composited layers on the

The branch returns **after** every hook in the component. React requires
the same hooks in the same order on every render; what the branch skips
is the rendering, which is where the cost is.

The insights carousel keeps drag, autoplay, arrows, the dot rail and the

### Responsive sweep — seven viewports

`npm run audit:responsive` walks three routes at each of 320, 360, 390,
414, 768 and 1024 wide, plus phone landscape at 844x390 — the widths
the two-viewport site audit does not cover. 320px is the narrowest
viewport still in real use (iPhone SE 1st gen, Galaxy Fold closed) and
the first place a fixed width or an unbroken word pushes a page
sideways; landscape is where `svh`-based layouts usually come apart,
since 390px of height has to hold a section built for a tall viewport.

**Every viewport clean.** No horizontal scrolling, nothing reachable
past the right edge, no touch target under 24px, no page errors.

The first run reported failures at all seven, and all of them were the
checker's fault: it flagged any element extending past the right edge,
which on this site means the carousel's peeked neighbour slides, the
capability wall's marquee rows, and anything under `clip-x` on the app
root. Those are placed outside the viewport deliberately and clipped.
The check now walks up for a clipping ancestor first, and the real
test — `documentElement.scrollWidth` against the viewport — was
reporting zero the whole time.

One standing observation, not a defect: the `text-meta-sm` token is
0.625rem, so nav links, eyebrows and button labels render at **10px**.
It is applied consistently and it is the site's established micro-label
scale, but it is the smallest type here and worth a deliberate look on
a phone rather than an assumption. Left alone.

# Next.js migration — 22 August 2026

Vite 6 + React 18 + React Router 6 → **Next 16.3 (App Router, static
export) + React 19**. Tailwind, motion, the image pipeline, every
component and every audit stayed.

The requirement was that nothing on screen changes. That is a claim
about pixels, so it was checked in pixels: forty-eight full-page
captures — every route at 390px and 1440px — taken from the Vite build
before the port and from the export after it, and compared byte by byte.
The harness is `scripts/snapshot.mjs` and `scripts/snapshot-diff.mjs`,
and getting it to mean something took four attempts; see *Making the
comparison honest* below.

## What moved, and what did not

| | Before | After |
|---|---|---|
| Router | `react-router-dom` | App Router + `usePathname` |
| Per-route documents | `scripts/seo-build.mjs`, 500 lines of string substitution over `dist/index.html` | `generateMetadata` per route + `src/lib/seo.ts` |
| Sitemap | hand-built XML in the same script | `app/sitemap.ts` |
| llms.txt | same script | `app/llms.txt/route.ts`, `force-static` |
| 404 | shell rewritten by the same script | `app/not-found.tsx` |
| Hero preload | regex over `dist/assets` for a hashed filename | `src/lib/hero-image.ts` + `ReactDOM.preload` |
| Images | `<Picture>`, `scripts/images.mjs` | unchanged |
| Audits | 11 scripts | unchanged, plus `audit:csp` |

`scripts/seo-build.mjs` is deleted. It existed only because a
client-rendered SPA emits one document and Vite has no idea the other
twenty-two URLs exist. Next knows.

## The one real incompatibility: image imports

Vite resolves `import cover from './cover.webp'` to a URL string. Next
resolves it to a `StaticImageData` object. `IMAGES` in
`image-fallbacks.generated.ts` is *keyed by URL*, so an object key
stringifies to `"[object Object]"`, every lookup in `<Picture>` misses,
and the image silently drops to an unrecognised `src` — which renders
nothing and throws nothing.

Resolved at one boundary, `src/lib/asset.ts`: a five-line function with
a `typeof` check. The alternative was a webpack rule or a Turbopack
loader teaching the bundler to return strings — invisible from the code,
specific to one bundler's internals, and liable to break on exactly the
kind of major upgrade this project had just been through.

## Why the application is client-rendered

`app/_components/AppShell.tsx` loads the app with `{ ssr: false }`. That
is deliberate, and the full argument is in that file. The short version:
**what this site renders is a function of the viewport in seven places**,
and they branch on structure and copy, not on colour —

- selected work is a scroll-linked deck of ten pinned frames above
  768px and a plain list below it: different components;
- a project page's standfirst is the lede above `sm` and the shorter
  summary below it: different sentences;
- the insights carousel fills or contains each photograph, and draws its
  mirrored side panels only where there is slack;
- the hero's portrait blur is 35px on a desktop and lighter on a phone;
- the experience rail scroll-locks on a wide screen only.

A static export has one document for every device. Server-rendering that
tree means committing the file to the desktop branch, and every phone
then downloads it, paints it, and holds it until hydration finishes —
several hundred milliseconds of the wrong layout followed by a reflow.
That is a worse first paint than painting nothing, and it is measured in
Cumulative Layout Shift.

Nothing a search engine reads is given up. Every one of the twenty-three
documents carries its title, description, canonical, Open Graph, Twitter
card, a JSON-LD `@graph`, the page's real prose in `<noscript>`, and —
on the thirteen routes that paint it — a preload for the hero portrait
resolved to the exact rendition the browser will pick.

The single line that changes this is `{ ssr: false }`. Everything else
in `app/` is already written for either mode. When the seven branches
become CSS, that is the whole change.

## Routing: the modal route is why `App.tsx` still switches

`/insights/<slug>` renders the same page as `/` with a story open over
it. In Next those are different route segments, so navigating between
them would swap one page subtree for another — unmounting the carousel
and the hero, replaying the intro, losing the scroll position, every
time a card is opened or closed.

So the app is mounted **once, in the root layout**, and reads the
pathname itself. React reconciles `Home` across `/` and
`/insights/<slug>` exactly as React Router made it. Next's router keeps
doing what it is better at: giving each URL a document.

One consequence, and it is worth knowing: every `<Link>` on the site
navigates with `scroll={false}` (`src/components/Link.tsx`) and
`ScrollManager` owns the scrollbar alone. Two systems with three rules
between them is how a page ends up jumping once and then jumping back.

## SEO: verified identical, not assumed

A throwaway script compared `dist/` and `out/` route by route on title,
description, canonical, all ten `og:` tags, all four `twitter:` tags,
the full JSON-LD `@graph` node by node, and the `<noscript>` prose:

```
23 routes: head, JSON-LD and noscript identical
```

One thing needed forcing. Next's metadata resolver normalises URLs
against `trailingSlash: false` and strips the slash off an origin, so
`https://www.divyakush.com/` became `https://www.divyakush.com`. Same
URL to a browser; not the same string to the sitemap, to Search
Console's URL inspection, or to the crawl audit. The site has been
indexed under the one with the slash since it launched, so `app/_seo/`
writes the home canonical and `og:url` as literal tags and omits them
from the resolver.

`npm run seo:check` against the export: 23/23 unique titles, 23/23
unique descriptions, a real 404 for an unknown path, one finding — the
77-character title on `/insights/iit-ropar-complete`, which is a
deliberate choice and predates the port.

## Content-Security-Policy: one concession, argued and tested

`script-src` gained `'unsafe-inline'`. This is the only security posture
that changed, and it is not a shrug.

Next's export writes two executable inline scripts into every document:
a four-word bootstrap, identical everywhere, and the React flight
payload, different on all twenty-four documents by construction.
Hashing them is the right answer and does not fit this host — either one
`/*` policy carrying twenty-five hashes (~2.5KB of headers on every
response, including each of the 150 images a page pulls), or a per-path
policy per document, which needs Cloudflare Pages to *override* rather
than *combine* a duplicated header. Two CSP headers are enforced as
their intersection, so if Pages combines, the whole site stops
executing. That is a blank-page failure resting on undocumented
behaviour.

What it costs here: nothing on this site renders attacker-controlled
markup — no user content, no reflected query parameter, and the one
`dangerouslySetInnerHTML` is the JSON-LD block, generated from the
project's own data and escaping `<`. It is a loss of defence in depth,
not of a control that was stopping anything.

Two things were added to compensate:

- **`scripts/serve-dist.mjs` now parses and applies `public/_headers`.**
  Until it did, every audit ran against a server with no CSP, no
  security headers and no caching rules — which is to say, not against
  the site being shipped.
- **`npm run audit:csp`** loads every kind of route with the real policy
  attached and fails on any violation, on three independent signals:
  `securitypolicyviolation` events, console refusals, and whether the
  page rendered at all.

That audit immediately earned its place: GA4's tag loads a 1x1 from
`googletagmanager.com/a` on every page, which `img-src` did not allow.
Six pages, silent, would have shipped.

## Google Analytics 4 — G-59EFGHFFHF

Added as two `next/script` tags with `afterInteractive`: the loader from
`googletagmanager.com`, then `/ga.js`.

The bootstrap half of Google's snippet is a **file on this origin**
rather than the inline block Google ships, and that is the whole reason
`script-src` did not need a second concession. Verified end to end

## Three bugs the port surfaced

1. **motion 13 broke the deck.** Upgrading motion 11 → 13 collapsed all
   thirteen desktop pages that render the home page to an empty
   viewport, with `Failed to execute 'animate' on 'Element': Offsets
   must be null or in the range [0,1]`. motion 13 hardware-accelerates a
   scroll-linked value by handing it to the Web Animations API, and the
   deck's `windows()` deliberately produces input ranges outside
   `[0, 1]` — `exitTo` for the last frame is 1.058, because the last
   frame is not supposed to exit. Legal as an interpolation domain,
   illegal as a WAAPI offset.

   **motion is pinned to ^11.18.2**, the line the site was built and
   tuned against. A port should change one thing. The fix, when it is
   taken: clip each input range to `[0, 1]` and interpolate the output
   ends proportionally, so the mapping is unchanged and the offsets are
   legal.

2. **Every prefetch 404'd.** Next 16 prefetches a route by fetching its
   per-segment RSC payload. The export writes those nested —
   `out/projects/netra/__next.projects/$d$slug/__PAGE__.txt` — and the
   client requests them dot-joined —
   `/projects/netra/__next.projects.$d$slug.__PAGE__.txt`. On Vercel
   something reconciles the two; on a static host nothing does. The site
   audit found it as **33 HIGH findings, all of them a hover over a
   project link**. `scripts/post-build.mjs` now writes a copy at the
   requested name, and fails loudly if the layout ever changes.

3. **Two hero preloads per document.** React hoists a
   `<link rel="preload" as="image">` as written *and* registers it as a
   resource and emits its own canonical copy. Both named the same
   srcset, so the browser fetched once and nothing looked wrong — the
   kind of duplication that survives for years. Going through
   `ReactDOM.preload()` emits exactly one. Found by an assertion in
   `post-build`, not by reading the HTML.

Two smaller ones: a ref callback with an expression body
(`ref={(el) => (refs[i] = el)}`) is a cleanup function in React 19, and
the hero's `fetchpriority` workaround for React 18's unknown-property
warning had become the thing it was working around.

## Making the comparison honest

The pixel harness reported differences three times before it reported
the truth, and each cause is worth keeping:

- **Cold cache.** The first baseline caught five story overlays with an
  empty frame because `networkidle` fires before a large WebP has
  decoded. It now waits on `img.complete`.
- **A live clock.** The footer prints IST to the minute, so two captures
  either side of a minute boundary differ by two glyphs. Freezing
  `Date` globally *broke the page* — the animation library reads the
  clock for frame deltas, and a frozen clock produced an offset outside
  `[0,1]`. The shim is now as narrow as the problem: only a formatter
  asking for `Asia/Kolkata` is pinned.
- **Subpixel antialiasing.** Chromium picks grayscale or LCD
  antialiasing per compositing layer, and whether a run of text gets its
  own layer depends on whether an animation left a transform behind.
  Two runs of the *same build* disagreed on three chip labels.
  `--disable-lcd-text` forces grayscale.
- **A shared HTTP cache.** One context per viewport meant which rung of
  an image ladder a page painted depended on what the pages before it
  had loaded. One context per page now; cold, both builds pick the same
  file every time.
- **Lazy loading behind a modal.** On an insight route the story overlay
  pins the body, so the harness's scroll-through moves nothing, no lazy
  image below the fold ever enters the viewport, and the ten project
  covers behind the overlay stay empty — or do not, depending on whether
  the app booted before the scroll started. Both builds mark exactly the
  same 32 images lazy and load exactly the same 27 with the overlay
  closed, so the attribute was never the difference. The harness strips
  `loading` before the page's own script runs.
- **Full-page capture of a pinned page.** The last one, and the one that
  mattered. A full-page screenshot asks Chromium to paint beyond the
  viewport; with the body `position: fixed` for the scroll lock, the
  document still lays out to 27,000px and the scroll-linked deck behind
  the overlay resolves differently depending on how that pass runs.
  Captured twice from the *same* build, one route differed by 1.407%.
  Captured once from each build, the two were identical — **0.000%**.
  The noise was larger than the signal it was meant to detect. Modal
  routes are now captured at viewport size, which is also the honest
  frame: the overlay is fixed and covers the screen, and the page
  underneath is already captured in full by `/`.

# Certifications hover, and the SEO the port left stale — 22 August 2026

## The bug: hovering one certificate blanked the one beside it

Reported as "hover a certificate, move the cursor out, the one next to
it disappears for a second or two". It reproduced, and the cause was
not in the neighbour at all.

Three measurements off the built export, at 1500x1000 with the GPU on:

| | before | after |
|---|---|---|
| composited layers, at rest | 52 | 27 |
| composited layers, one card hovered | 67 | 27 |
| how long the card keeps mutating after the pointer leaves | 795ms | 462ms, then released to `transform: none` |

A single hover was taking the page from 52 composited layers to 67 and
holding it there for the best part of a second. Three things did that,
and all three were fixed in `src/components/CertificationsWall.tsx`:

1. **`filter: grayscale()` and `transform: scale(1.03)` animating
   together on the same `<img>`.** A CSS filter resolves at raster
   time, so animating one *while the element is being scaled* makes the
   browser run a fresh full-size filter pass over a 1414x1000 source on
   every frame — eighteen of these on the page, sharing one raster
   budget. When that budget is exceeded Chromium serves blank tiles for
   whatever it has not finished, which is the disappearance. The zoom
   now lives on a wrapper with no filter; the filter animates at a
   fixed size where its result can be rastered once per step and
   reused.

2. **The tilt spring never stopped.** Measured at 5.7e-13 degrees still
   animating 733ms after the pointer left. motion drives this through
   the Web Animations API, and a running animation on `transform` pins
   the element to its own layer for as long as it runs. `restDelta:
   0.05` ends it when it stops being visible rather than when the float
   maths runs out — a hundred-and-fortieth of a 7 degree tilt.

3. **`transformStyle: preserve-3d` on all eighteen buttons.** Nothing
   inside them is positioned in 3D, so it bought nothing, and it put
   the whole grid into a permanent 3D rendering context that the
   compositor cannot flatten or cache. Removing it alone halved the
   at-rest layer count.

Two smaller things fell out. `transform` was in the button's CSS
`transition` list while motion rewrote that same property every frame,
so a 300ms interpolation restarted on every frame; it is out of the
list now. And `motion-safe:hover:-translate-y-1` had never rendered on
any device — an inline transform beats a class one — so the intended
lift was dead on arrival, and it was the only reason `transform` was in
that list. It is removed rather than silently switched on: making it
work is a design decision, not a bug fix.

### The unexpected part

Fixing this made a photograph on a different page render **better**.
`/insights/nec-visionary-ventures` came back 4.1% different from the
baseline, entirely inside the story photograph, as a pure edge map —
the signature of a resampling change, not a layout shift. Mean
absolute laplacian over the photo went 10.5 to 12.1: the new render is
sharper, same framing, no ringing. The certifications section had been
consuming enough compositing budget to push photographs elsewhere on
the page onto the GPU's bilinear path.

Both states are reachable on both the old and the new code — this
image and `/insights/iit-ropar-complete` are bistable in the harness —
and the fix biases toward the sharp one. **A clean run of the finished
build is 48 of 48 pixel-identical to `.baseline`.**

## SEO and GEO

Verified first, then extended. Nothing here was broken; the gaps were
things the Vite-era build never had and the port did not add.

**Verified as shipping:** `robots.txt`, `sitemap.xml` and `llms.txt` all
200 with correct content types under the real `_headers`; 23/23 unique
titles and descriptions; a real 404 for an unknown path; and **0
dangling @id references across all 23 JSON-LD graphs** — every @id
reference resolves to a node in the same document.

**Added:**

- **`Article.datePublished` on all twelve insight routes.** They
  carried no date at all, which makes an Article ineligible for several
  of Google's article treatments outright and gives an answer engine
  nothing to weigh for recency. `isoDate()` in `src/lib/seo.ts` parses
  what the caption rail prints — "2024", "Jun 2025", "13 July 2025",
  and ranges like "23 Mar to 20 Jul 2025", which resolve to their end
  because a credential's date is the date it was awarded. Reduced
  precision in, reduced precision out: "2025-06" is a complete ISO 8601
  date and it is the true one. Padding a month out to -01 to quiet a
  validator asserts a day nobody has.
- **`Person.hasCredential` — twelve credentials**, each with issuer,
  category, date and, where the document prints one, its credential
  number. All twelve dates parse. This is the strongest entity signal
  on the site: a name is a string, but a person holding named
  credentials from named organisations on named dates is something a
  knowledge graph can place. Attached to the home page's Person node
  only — same @id everywhere, so a consumer assembling the graph gets
  the full description from the page that is *about* the person, and
  four kilobytes are not repeated on twenty-three documents.
- **`Person.description`**, and **`inLanguage`** on Article.
- **`ImageObject` width and height** on insight primary images, read
  off the files by `scripts/images.mjs` rather than typed. A hand-written
  dimension is wrong the first time a photograph is recropped,
  silently.

Measured cost of all of it: the home document went 19.1KB to 25.8KB and
LCP did not move. Three runs with the credential block removed gave
2408-2512ms; three runs with it gave 2432-2492ms. The JSON-LD is in the
body and the hero preload sits at byte 155 of a 3.9KB head, so it was
never in the way.

**`sitemap.xml` lastmod was the build time, on every URL, on every
deploy.** The old comment defended that as honest because a static
export is rewritten in full each time — true about the files, but not
what the field means. Google uses lastmod when it is demonstrably
accurate and ignores it when it is not, and "all twenty-three changed
just now, again" is how a site teaches it to stop reading the field.
It now comes from the last commit touching each route's data file, with
the build date as a fallback where git is unavailable. Redeploying
without changing content leaves the dates alone, which is the point.

**Declined:** `Article.dateModified`. Nothing tracks when a story was
last edited, and emitting the build date would claim all twelve are
revised on every deploy — the same mistake the lastmod fix just
corrected.

# Three post-deploy fixes — 22 August 2026

The site went live on Cloudflare Pages. Verified against production,
not localhost: twenty-three routes answering 200 with distinct titles,
a real 404, and every security header from `public/_headers` applied by
Cloudflare. The distinct titles are the proof that matters — the site
this replaced served `/* /index.html 200`, so every URL reported the
home page's title and canonical. That is fixed in production now.

Three things surfaced afterwards.

## 1. The document title never reverted to the home page's

Closing a story left the tab named after the story. Measured on the
export and again on production:

    /            -> /projects/x   title updates          ok
    /projects/a  -> /projects/b   title updates          ok
    /insights/x  -> /             title stays on the story
    /projects/x  -> /  (Back)     title goes EMPTY

In the same navigations the description, `og:title` and canonical all
reverted correctly, so this was not metadata failing to resolve. It was
the `<title>` element specifically, and only for the root route.

Four candidate causes were tested and each ruled out by measurement:
the explicit `<head>` element in the root layout, the layout-level
`title`, a static `metadata` export versus `generateMetadata` on the
home page, and React's `<title>` hoisting. None changed the result.

`TitleManager` in `src/App.tsx` now sets the title on pathname change,
reading `titleFor()` — which resolves through `homeSeo`/`projectSeo`/
`insightSeo`, the same table `app/` uses to write the served HTML. One
source of truth, so a route cannot end up with two answers. It is a
no-op on every navigation Next already gets right, including first
paint of every URL.

`INSIGHT_PREFIX` moved into `src/lib/seo.ts` as part of this. It was a
local constant in `InsightsCarousel.tsx` whose own comment warned
against a second copy, and the App shell needed it too.

## 2. The insights dot rail wrapped on every phone

Twelve dashes, and one fell onto a second line at every width below
414px. Measured: 334px of items against 270px of content width at
320px, 310px at 360px, 340px at 390px.

`flex-wrap` is gone, so it has to fit. The arithmetic is the whole
problem: twelve targets at the 24px minimum need 288px, and a 320px
phone does not have that after gutters.

The first attempt shrank the targets to 20x40 and the audits caught it
immediately — two MED findings, on `/` and every insight route, where
there had been none. So the targets stay at 24px and the rail is
allowed to run *into* the gutter instead: 302px of items centred in a
270px container extends 16px each side, the gutter is 25px, and
`documentElement.scrollWidth` is unchanged from 320px up. Checked
rather than assumed, because a nowrap row is exactly how a page
acquires a horizontal scrollbar.

Below `sm` the button padding is 7px and the active mark 24px; above
it, the original 8px and 32px, so nothing on a desktop moved. The pixel
harness confirms it: `home-phone.png` is 40px shorter than the baseline
— one `h-10` row, the wrapped one — and `home-desktop.png` is
identical.

## 3. Two console errors, both from Cloudflare, neither from this repo

Zero console errors locally, two in production. Both are injected by
the platform after the export leaves the build.

**The Web Analytics beacon was blocked by our own CSP.** Pages injects
`static.cloudflareinsights.com/beacon.min.js` into every HTML response
when Web Analytics is on, and `script-src` had never heard of it. The
host is allowed now. The cleaner fix is arguably to turn Web Analytics
off — GA4 already measures this site, so the beacon is a second vendor
collecting the same page views — but a CSP that blocks a script its own
host injects argues with the platform on every request, and nobody
reading a console can tell that apart from a real attack.

**Early Hints preloads a URL that does not exist.** Cloudflare scrapes
the HTML to build `103 Early Hints` and does not decode HTML entities,
so it emits:

    Link: <https://fonts.googleapis.com/css2?family=Inter:...
           &amp;family=JetBrains+Mono:...&amp;display=swap>; rel="preload"

with the `&amp;` literal. That is a different URL from the stylesheet
the page actually loads, so the browser preloads it, never uses it, and
logs `preloaded using link preload but not used within a few seconds` —
once per hint.

Nothing in this repository is wrong: `&amp;` is the correct escaping
for `&` in an HTML attribute, and the DOM's own `href` contains a plain
`&`. This is a Cloudflare defect and the fix is theirs or a toggle:
**Speed → Optimization → Early Hints, off**. The code-level alternative
is `next/font`, which would self-host Inter and JetBrains Mono and
remove the external stylesheet — and the URL — entirely. That remains
the open typography decision.
